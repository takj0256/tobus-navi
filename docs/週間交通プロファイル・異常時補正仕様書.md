# 都バスナビ 週間交通プロファイル・異常時補正仕様書

文書版：1.0  
作成日：2026年8月4日  
対象：Phase 11（Phase 10の停留所イベント型位置推定を拡張）

---

## 1. 目的

都営バスの公開GTFS-RTから得られる停留所到着イベントを継続的に集計し、路線・方向・停留所間・曜日区分・時間帯ごとの標準所要時間を作成する。

通常時は週間プロファイルだけで停留所間位置と到着時刻を推定し、実際の到着が予測から大幅に外れた場合に限り、外部交通APIへ照会して渋滞・事故・通行止めを補正する。

本方式の目的は次の3点である。

- 交通APIの無料枠内で、現在の道路状況を必要時だけ利用する
- 時刻表だけでなく、実際の曜日・時間帯に固有の遅れを通常モデルへ反映する
- 交通APIが利用できない場合も、週間実績とGTFS時刻表だけで動作を継続する

## 2. 前提と制約

### 2.1 公開位置情報の性質

- 都営バスの公開フィードは、連続的な車載GPS軌跡としては扱わない。
- `stop_id` または `current_stop_sequence` の変化を停留所イベントとして扱う。
- 停留所間の表示位置は、直前の停留所イベントと推定区間時間から算出した推定値である。
- 異常の確定は原則として次の停留所イベント受信後になるため、渋滞の検知は最大1区間遅れる。

### 2.2 Phase 10から引き継ぐ機能

- 車両別の停留所イベント履歴
- 連続停留所イベントからの区間実測時間生成
- 外れ値を抑えた中央値
- GTFS時刻表へのフォールバック
- 推定進行率94%上限
- 後続到着時刻の単調増加保証
- 端末内履歴の最大14日保存

### 2.3 用語

| 用語 | 定義 |
|---|---|
| 区間 | 同一便で連続する2停留所間 |
| 区間実測時間 | 前停留所イベントから次停留所イベントまでの秒数 |
| 週間プロファイル | 過去の区間実測時間を曜日区分・時間帯別に集計した標準値 |
| 基準時間 | 週間プロファイルとGTFS時刻表から算出した通常時の区間所要時間 |
| 到着乖離 | 実際の停留所イベント時刻と予測到着時刻との差 |
| 異常状態 | 到着乖離または区間時間比が閾値を超えた状態 |
| 外部補正 | 交通APIの速度・所要時間・インシデント情報による一時的な補正 |

## 3. 対象範囲

### 3.1 対象

- 全都営バス系統の方向別・停留所区間別所要時間
- 平日、土曜、休日の曜日区分
- 15分単位の時間帯プロファイル
- 到着乖離の検知
- 異常時だけの交通API照会
- 同一路線周辺車両への補正結果共有
- API障害・無料枠枯渇時のフォールバック

### 3.2 対象外

- バス車内からの連続GPS送信
- 信号現示、乗降人数、天候を直接使う予測
- 事故原因の特定
- バス経路そのものの変更判断
- 外部交通APIが示す一般車向け迂回路へのバス経路変更

## 4. 全体構成

```text
ODPT GTFS-RT
    │
    ├─ ブラウザ/PWA ─ 現在表示中の車両を10秒周期で更新
    │                    └─ 端末内の暫定区間履歴
    │
    └─ Cloudflare Worker ─ 停留所イベント収集
                           ├─ 区間実測時間を保存
                           ├─ 週間プロファイルを定期生成
                           ├─ 到着乖離を判定
                           └─ 異常時のみ交通APIへ照会
                                      │
                                      └─ TomTom Traffic等

ブラウザ/PWA
    └─ Workerから週間プロファイルと一時補正を取得
       └─ ETA・停留所間進行率・説明表示を更新
```

共有プロファイルを実現する場合、ブラウザの`localStorage`だけでは不十分である。アプリを開いていない時間も収集するため、Worker側に収集処理と永続ストレージを置く。

## 5. データ識別子

区間は次の組合せで一意に識別する。

```text
route_id | direction_id | from_stop_id > to_stop_id
```

`trip_id`は日ごと・便ごとに変化し得るため、週間プロファイルの主キーには使用しない。ただし、イベントの重複排除と同一便判定には使用する。

方向IDが欠損する場合は、次の優先順位で方向スコープを決定する。

1. `direction_id`
2. 静的GTFSの停留所順序と終点IDから生成した方向キー
3. `route_id + headsign`の正規化値

## 6. 収集仕様

### 6.1 停留所イベント

次の項目を収集する。

```json
{
  "event_id": "vehicle_id:trip_id:stop_sequence:timestamp",
  "vehicle_id": "bus-123",
  "trip_id": "trip-456",
  "route_id": "route-1",
  "direction_id": 0,
  "stop_id": "stop-B",
  "stop_sequence": 12,
  "observed_at": "2026-08-04T08:12:31+09:00",
  "feed_timestamp": 1785798751
}
```

### 6.2 区間実測時間の生成条件

同一車両の直前イベントと現在イベントが次をすべて満たす場合だけ、区間サンプルを生成する。

- 同一`trip_id`
- 停留所IDが異なる
- `stop_sequence`差が1。欠損時は静的GTFS上で連続している
- 経過時間が15秒以上1,800秒以下
- 同一`event_id`または同一区間到着イベントが未登録

条件を満たさないイベントは監査ログへ理由を記録し、学習値には使用しない。

### 6.3 保存期間

| データ | 保存期間 | 用途 |
|---|---:|---|
| 車両直近イベント | 30分 | 区間サンプル生成 |
| 区間サンプル | 28日 | 週間プロファイル生成と前週比較 |
| 週間プロファイル | 現行＋直前4版 | ロールバック・評価 |
| 外部交通API応答 | 10分 | 重複照会防止 |
| 異常状態 | 最大60分 | 一時補正 |
| 監査ログ | 14日 | 障害解析 |

生の利用者位置情報は保存しない。

### 6.4 ストレージ構成

全車両の停留所イベントをD1へ1行ずつ保存すると無料枠の行書き込み上限を超える可能性があるため、生イベントと集計結果を分離する。

| 保存先 | 保存内容 | 書き込み単位 |
|---|---|---|
| R2 Standard | 1分ごとの区間イベントバッチ、1時間ごとの統合バッチ | 1ポーリングにつき最大1オブジェクト |
| D1 | 週間プロファイル、異常状態、有効補正、交通API使用量 | 集計済み行だけ |
| Workers Cache | 外部交通APIの正規化応答 | 道路区間ごと、5～10分 |

毎分オブジェクトは1時間ごとに1個の時間バッチへ統合し、元オブジェクトを削除する。日次集計は直近28日分の時間バッチを読み、中央値、四分位、MADをWorker側で計算する。D1のSQLにパーセンタイル関数が存在することを前提にしない。

R2またはD1のバインディングがない環境では収集APIを無効化し、既存のGTFS-RT中継とPhase 10の端末内履歴だけを継続する。

## 7. 週間プロファイル仕様

### 7.1 集計軸

```text
区間キー × 曜日区分 × 15分時間帯
```

曜日区分は次の3種類とする。

- `weekday`：月曜～金曜。ただし休日を除く
- `saturday`：土曜。ただし休日を除く
- `holiday`：日曜および祝日

祝日判定には更新可能な日本の休日カレンダーを使用する。年末年始や臨時ダイヤは別サービス区分を設定できる構造にする。

### 7.2 集計対象期間

- 基本窓：直近7日
- 最低サンプル不足時：直近28日まで段階的に拡張
- 直近24時間の異常状態中サンプルは、通常プロファイルへ即時混入させない
- 同じ異常が複数週継続した場合のみ、通常傾向候補として次回生成時に採用する

### 7.3 統計量

各プロファイルに次を保存する。

```json
{
  "segment_key": "route-1|0|stop-A>stop-B",
  "day_type": "weekday",
  "time_bin": "08:00",
  "median_seconds": 185,
  "p25_seconds": 164,
  "p75_seconds": 228,
  "mad_seconds": 31,
  "sample_count": 24,
  "scheduled_seconds": 150,
  "profile_ratio": 1.233,
  "confidence": 0.86,
  "generated_at": "2026-08-04T04:05:00+09:00"
}
```

平均値は参考値として保存してよいが、基準時間には外れ値の影響を受けにくい中央値を使用する。

### 7.4 サンプル数不足時の縮約

15分枠のサンプル数が不足する場合は、次の順で対象を広げる。

1. 同じ曜日区分・前後15分を含む45分枠
2. 同じ曜日区分・前後30分を含む75分枠
3. 同じ曜日区分・同一時間帯の直近28日
4. 同一区間の全時間帯中央値
5. GTFS時刻表

最低有効サンプル数は3、通常採用目標は8以上とする。

### 7.5 信頼度

プロファイル信頼度は0～1で表す。

```text
sample_score    = min(1, sample_count / 12)
spread_score    = clamp(1 - (p75 - p25) / median, 0, 1)
freshness_score = 直近7日サンプル比率

confidence = 0.50 × sample_score
           + 0.30 × spread_score
           + 0.20 × freshness_score
```

## 8. 通常時推定

### 8.1 区間基準時間

```text
confidence < 0.3 の場合:
    profile_weight = 0

confidence >= 0.3 の場合:
    profile_weight = min(0.85, 0.65 × confidence)

base_seconds = scheduled_seconds × (1 - profile_weight)
             + bounded_profile_seconds × profile_weight
```

`bounded_profile_seconds`はGTFS時刻表値の0.5～3.0倍に制限する。

### 8.2 直近先行車の反映

45分以内に同一区間を通過した先行車が2件以上ある場合、Phase 10の直近実績を重ねる。

```text
recent_weight = min(0.55, 0.15 + 0.10 × recent_sample_count)

normal_seconds = base_seconds × (1 - recent_weight)
               + recent_median_seconds × recent_weight
```

直近実績がない場合は`normal_seconds = base_seconds`とする。

### 8.3 進行率

```text
elapsed = 現在時刻 - 直前停留所イベント時刻
progress = clamp(elapsed / estimated_segment_seconds, 0, 0.94)
```

次停留所イベントを受信するまで100%到着とは表示しない。

## 9. 異常検知

### 9.1 判定値

次停留所イベントを受信した時点で計算する。

```text
arrival_deviation_seconds = actual_arrival - predicted_arrival
segment_ratio = actual_segment_seconds / expected_segment_seconds
```

### 9.2 初期閾値

次のいずれかを満たした場合、異常候補とする。

- 到着が予測より120秒以上遅い
- 実測区間時間が予測の1.5倍以上
- 実測区間時間が`p75 + 2 × MAD`を超える
- 進行率94%上限の状態が90秒以上継続する

単一の異常サンプルだけで路線全体を補正しない。次のいずれかで異常を確定する。

- 同じ車両で連続2区間が異常
- 10分以内に同一区間または隣接区間の2車両が異常
- 同一区間または同一異常クラスタに有効期限内の交通APIキャッシュがあり、渋滞、事故または通行止めを示す

ただし、到着乖離が300秒以上の場合は単独でも重大異常として即時照会する。

異常確定のために新しい交通API照会は行わない。確定判定で参照できるのは、別車両の重大異常などにより既に取得済みのキャッシュだけとする。新規照会は、上記条件による異常確定後または300秒以上の重大異常時に行う。

### 9.3 誤検知の除外

次の場合は交通API照会のトリガーにしない。

- GTFS-RTフィード自体が90秒以上古い
- `trip_id`が途中で変化した
- 連続しない停留所へジャンプした
- 始発待機、終点折返し、運行打切りと判断できる
- 静的GTFSの予定停車時間内である
- 同一区間のサンプルが欠損し、予測信頼度も0.3未満である

## 10. 外部交通API照会

### 10.1 利用方針

初期アダプターはTomTom Traffic Flow Segment Data相当を想定する。ベンダー依存処理はWorker内の`TrafficProvider`インターフェースに隔離し、将来JARTICや別サービスへ交換できる構造にする。

APIキーはWorkerのSecretとして保存し、ブラウザへ返さない。

### 10.2 照会地点

停留所間の直線中点ではなく、静的GTFSのshape上で区間中央に相当する道路座標を使用する。shapeがない場合のみ、両停留所の中点を使用する。

### 10.3 正規化応答

```json
{
  "segment_key": "route-1|0|stop-A>stop-B",
  "provider": "tomtom",
  "observed_at": "2026-08-04T08:17:00+09:00",
  "current_travel_seconds": 240,
  "freeflow_travel_seconds": 150,
  "traffic_ratio": 1.6,
  "confidence": 0.91,
  "road_closed": false,
  "incident": false,
  "expires_at": "2026-08-04T08:27:00+09:00"
}
```

### 10.4 照会抑制

- 同一区間は最短5分間再照会しない
- 隣接区間のキャッシュが同じ道路区間を示す場合は共有する
- 同じ異常クラスタに属する車両は照会結果を共有する
- 1時間、1日、1か月の上限値を設定ファイルで管理する
- 月間使用量が上限の80%に達したら重大異常だけ照会する
- 95%で新規照会を停止し、週間プロファイルへフォールバックする
- HTTP 429受信時は最低15分停止し、指数バックオフする

## 11. 外部補正

### 11.1 補正倍率

外部APIが有効な場合、次の倍率を求める。

```text
api_ratio = current_travel_seconds / freeflow_travel_seconds
bus_ratio = recent_observed_seconds / base_seconds

correction_ratio = 0.50 × clamp(api_ratio, 0.7, 3.0)
                 + 0.30 × clamp(bus_ratio, 0.7, 3.0)
                 + 0.20 × 1.0
```

バス実績が1件もない場合は、API 60%、週間基準40%とする。API信頼度が0.5未満の場合は、API重みを半減して週間基準へ振り替える。

### 11.2 補正対象

- 異常を検知した区間
- 同じshape上の後続2区間
- 10分以内に同じ道路を通る同方向の他車両

路線全体や反対方向へは自動適用しない。

### 11.3 補正の減衰

補正は永久保存せず、最終異常またはAPI応答から時間と距離に応じて減衰させる。

```text
effective_ratio = 1 + (correction_ratio - 1)
                      × time_decay
                      × distance_decay

time_decay = max(0, 1 - elapsed_minutes / 30)

downstream_segment_count > 2 の場合:
    distance_decay = 0
それ以外:
    distance_decay = max(0, 1 - downstream_segment_count / 3)
```

これにより異常区間、後続1区間、後続2区間の距離係数は、それぞれ1.00、0.67、0.33となり、後続3区間目以降は必ず0になる。

次の条件で補正を解除する。

- 後続2台が基準時間の±20%以内で通過
- 30分経過
- 外部APIが通常状態を返し、直近バスも正常

## 12. API仕様

### 12.1 週間プロファイル取得

```http
GET /api/v1/profiles?route_id=...&direction_id=...&from_stop_id=...&to_stop_id=...&at=...
```

レスポンス例：

```json
{
  "profile_seconds": 185,
  "scheduled_seconds": 150,
  "confidence": 0.86,
  "sample_count": 24,
  "day_type": "weekday",
  "time_bin": "08:00",
  "generated_at": "2026-08-04T04:05:00+09:00"
}
```

### 12.2 現在補正取得

```http
GET /api/v1/corrections?route_id=...&direction_id=...&from_stop_id=...&to_stop_id=...
```

補正がない場合はHTTP 200で`active: false`を返す。

### 12.3 デバッグ情報取得

```http
GET /api/v1/debug/segments/{segment_key}
```

公開環境では管理者認証を必須とし、入力サンプル、除外理由、異常判定、API照会履歴を返す。

## 13. PWA表示仕様

通常表示では内部計算を過度に見せず、根拠を短く表示する。

| 状態 | 表示例 |
|---|---|
| プロファイル採用 | 平日8時台の運行実績24件から推定 |
| 直近実績採用 | 先行車3台の実績で補正 |
| 外部補正中 | 周辺道路の混雑を検知・到着予測を補正中 |
| 低信頼度 | 実績が少ないため時刻表中心の推定 |
| API停止 | 交通情報を取得できないため運行実績から推定 |
| 94%上限 | 次停留所の位置更新待ち |

外部APIによる補正値も「現在地の実測」と誤認させず、推定であることを明示する。

## 15. 障害時動作

優先順位は次のとおりとする。

1. 有効な外部補正＋直近バス実績＋週間プロファイル
2. 直近バス実績＋週間プロファイル
3. 週間プロファイル＋GTFS時刻表
4. 端末内Phase 10履歴＋GTFS時刻表
5. GTFS時刻表のみ

Worker、ストレージ、交通APIのいずれかが停止しても、時刻表表示とPhase 10の基本位置推定を停止させない。

## 16. プライバシーとセキュリティ

- 利用者端末のGPS座標はサーバーへ保存しない
- 保存対象は公開交通データから生成した車両・停留所イベントのみとする
- 外部APIキーはWorker Secretに保存する
- PWAからWorkerへの取得APIは読み取り専用とする
- 管理・デバッグAPIには認証とレート制限を設定する
- ログにはAPIキー、Cookie、利用者位置を出力しない
- CORSは本番公開ドメインへ制限できる設定を用意する

## 17. 監視項目

- GTFS-RT最終取得時刻とフィード年齢
- 生成した区間サンプル数と除外数
- プロファイル対象区間の網羅率
- プロファイルのサンプル数・信頼度分布
- 異常候補数、確定数、誤検知解除数
- 交通APIの日次・月次使用量
- 交通APIの成功率、429率、応答時間
- 補正あり／なしのETA誤差

## 18. 評価指標

主要評価値は停留所到着時刻の絶対誤差とする。

```text
MAE = mean(abs(predicted_arrival - actual_arrival))
```

次の3モデルを同一期間・同一便集合で比較する。

1. GTFS時刻表のみ
2. Phase 10（直近区間実績）
3. Phase 11（週間プロファイル＋異常時外部補正）

補助指標：

- 中央絶対誤差
- 90パーセンタイル誤差
- 2分以内的中率
- 異常検知の適合率・再現率
- 交通API 1,000回当たりのMAE改善秒数
- 月間API使用量

## 19. 受入条件

- 同一区間・曜日区分・15分枠ごとの中央値を生成できる
- サンプル不足時に定義順で縮約し、最終的にGTFSへフォールバックできる
- 通常時に外部交通APIを呼ばない
- 120秒または1.5倍の乖離を異常候補として検出できる
- 単発の軽微な遅れで路線全体を補正しない
- 重大異常時に外部APIを1回照会し、結果を最低5分再利用できる
- 補正が後続2区間を超えて無制限に伝播しない
- 補正が30分以内に減衰・解除される
- APIキーがクライアント配信物へ含まれない
- API停止・上限到達時もPhase 10相当の推定が継続する
- 推定値が停留所イベント到着を追い越さない
- テストデータでPhase 11のMAEがPhase 10以下になる。悪化する場合は本番採用しない

## 20. テスト仕様

### 20.1 単体テスト

- 15分時間帯の境界（07:59、08:00、08:14、08:15）
- 平日、土曜、日曜、祝日の分類
- 中央値、四分位範囲、MAD、信頼度
- 外れ値を含むサンプルの頑健性
- サンプル不足時の時間幅・期間拡張
- 異常候補、確定、重大異常の境界値
- 補正倍率の上下限
- 時間減衰と距離減衰
- APIキャッシュ、再照会抑止、月間上限

### 20.2 統合テスト

- ODPTイベントから区間サンプル、プロファイル、PWA表示まで
- 2車両の同一異常によるAPI照会
- API成功、タイムアウト、HTTP 429、不正JSON
- Workerストレージ停止時のフォールバック
- 古いGTFS-RTによる誤照会防止
- Service Worker更新後の旧形式キャッシュ移行

### 20.3 回帰テスト

Phase 10の次のケースを維持する。

```text
石島 → 扇橋一丁目：4分
扇橋一丁目 → 猿江一丁目：3分
石島イベントから猿江一丁目まで：約7分
```

週間プロファイルがない場合、Phase 10と同じ結果になることを確認する。

## 21. 段階導入

### Stage 1：観測のみ

- Worker側で区間サンプルと週間プロファイルを生成
- PWAの予測には使用しない
- 1～2週間、欠損率と分布を確認

### Stage 2：シャドー評価

- Phase 10とPhase 11の予測を同時生成
- 利用者表示はPhase 10のまま
- 到着後に両者の誤差を記録

### Stage 3：週間プロファイル採用

- 信頼度0.5以上の区間だけPhase 11を表示に採用
- 外部交通APIはまだ呼ばない

### Stage 4：異常時外部補正

- 無料枠上限とキャッシュを有効化
- 対象路線を限定して開始
- MAEとAPI消費量を確認後に拡大

## 22. 実装上の注意

- 「1週間の平均」を固定値として毎週上書きするだけでは、外れ値と曜日差に弱い。中央値、ばらつき、サンプル数、生成時刻を必ず一緒に保持する。
- 異常時の遅い実測を即座に通常プロファイルへ混ぜると、事故渋滞を翌週以降の通常状態として学習してしまう。異常サンプルは隔離する。
- 一般車の道路速度と、停留所で乗降するバスの所要時間は一致しない。交通API値で全置換せず、バス実績・週間基準と重み付きで合成する。
- 外部APIの経路検索結果がバスの正規経路と異なる場合、その所要時間を採用しない。必ずGTFS shapeまたは停留所列に対応する道路区間へ照会する。
- 最終採用は予測誤差の実測比較で判断し、見た目上滑らかな位置表示だけを評価基準にしない。
