# プロジェクトの共有前提

更新日：2026-09-11。機能の存在と本番での有効性は別々に確認する。

## 目的

近隣の都バス停留所、同じのりばから利用できる便、到着推定を分かりやすく表示するPWA。
同じ目的地・のりばを共有する枝線は、利用者がまとめて便を選べるようにする。

## 構成

| 部分 | 役割・主なコード |
| --- | --- |
| ブラウザ | 時刻表・停留所検索、端末内の実績学習、到着推定。`js/app.js`、`js/realtime.js` |
| 地図 | 別ページの道路中心の白地図、始点・行き先、枝線合流、推定バス位置。`js/route-map.js` |
| Worker | 公開配信中継、毎分の観測収集、異常判定、天気・交通補正、プロファイルAPI。`worker/worker.js` |
| R2 | 元イベント、時間・日単位データ、世代別のPhase 11統計JSON |
| サブPC | 昨日分の日次データ生成と直近28日分の集計。`tools/run_phase11_local_aggregation.sh` |
| D1 | 現在天気、交通補正、運用状態、R2障害時の旧プロファイル参照 |

重い日次統合はサブPCへ移行したが、時間単位のR2統合はWorkerに残っている。
サブPCで計算しても、結果のD1投入はD1の書き込み行数を消費する。

## 推定と表示

- 公開GTFS-RTを調査した際、座標は停留所に一致していた。連続GPSと扱わず、停留所切替から区間所要時間を学習する。配信仕様の変更時は再検証する。
- 次の停留所の観測を得るまで、推定進行率は94%を上限とする。
- 到着予測は次の停留所だけでなく、残り区間と停車時間を累積する。
- Phase 11は曜日区分・15分ビン・区間別の中央値、四分位、MAD、サンプル数、信頼度を使う。
- WorkerはR2の公開済みcurrent世代を優先し、取得・検証に失敗したときだけD1の旧プロファイルへ戻る。本番APIの参照元とgenerationで有効性を確認する。
- 信頼度やデータ不足に応じてPhase 10の履歴・時刻表等へフォールバックする。詳細な条件は `js/phase11.js` とテストを確認する。
- 遅延表示は公式の遅延証明ではなく、GTFS-JPの停留所時刻と到着予測幅の比較による見込み。位置情報が古い場合や幅が広い場合は「確認中」とする。
- 新規交通API照会は異常確定後。確定前の判断には既存キャッシュのみ利用する。補正は同方向の後続2区間までとし、継承した補正から再伝播しない。
- 天気・気温の補正は存在するが、イベント／マラソン等の交通規制を体系的に取得する機能は実装済みとしない。
- 地図の正式経路はGTFS shapeを優先し、不足時の概略線を正確な道路トレースと呼ばない。
- 車種表示は識別ルールが根拠。不明な車両の燃料方式を断定しない。

精度の採用判断には実測との比較が必要。お盆・夏休み・曜日・季節の偏りを考慮し、サンプル数だけで信頼性を断定しない。

現在の運用課題は [STATUS.md](STATUS.md)、判断理由は [DECISIONS.md](DECISIONS.md) を参照。
